# Архитектура Invoice Keeper

Три части в одном репозитории, общая база PostgreSQL. Всё поднимается одной командой `docker compose up`.

```
 Браузер ──► frontend (nginx + React SPA) ──/api/──► backend (Go, Gin, REST /api/v1)
                                                         │
 Telegram ◄──► bot (Go, отдельный процесс) ──────────────┤
                                                         ▼
                                                   PostgreSQL (volume pgdata)
```

| Сервис     | Технологии                        | Роль |
|------------|-----------------------------------|------|
| `frontend` | React 18 + TypeScript + Vite + Tailwind, nginx | Веб-панель: вход, список платежей, регулярные платежи, пользователи |
| `backend`  | Go, Gin, GORM, JWT, bcrypt        | REST API, роли и права, расчёт статусов, создание периодов, Swagger |
| `bot`      | Go, go-telegram-bot-api           | Напоминания за 7, 3 и 1 день и при просрочке, кнопка «Оплачено», меню действий (`/menu`, `/upcoming`, `/overdue`, `/pay`, `/summary`, `/renew`…) |
| `db`       | PostgreSQL 16                     | Хранение; миграции применяет `backend` при старте |

`backend` и `bot` собираются из одного Go-модуля и **переиспользуют один сервисный слой** — бизнес-правила (статусы, просрочка, «без дублей») существуют в одном месте.

## Структура репозитория

```
invoice-keeper/
├── docker-compose.yml        # db + backend + bot + frontend
├── .env.example              # шаблон настроек (без секретов)
├── Makefile                  # make up / down / logs / test
├── docs/ARCHITECTURE.md
├── backend/
│   ├── api/openapi.yml       # OpenAPI 3 (встроена в бинарник, отдаётся на /api/v1/docs)
│   ├── migrations/*.sql      # SQL-миграции (embed), применяются при старте
│   ├── cmd/
│   │   ├── server/main.go    # точка входа API + фоновое создание периодов
│   │   └── bot/main.go       # точка входа Telegram-бота
│   └── internal/
│       ├── config/           # переменные окружения
│       ├── models/           # сущности, тип Date
│       ├── db/               # подключение + раннер миграций
│       ├── store/            # доступ к данным (GORM), без бизнес-логики
│       ├── service/          # бизнес-логика: auth, users, payments, budget, settings, audit, seed
│       ├── middleware/       # JWT-аутентификация, проверка ролей, CORS
│       ├── handler/          # HTTP-обработчики и роутер
│       ├── notify/           # email (SMTP) и webhook: события и напоминания
│       └── telegram/         # бот
└── frontend/
    ├── Dockerfile, nginx.conf
    ├── tailwind.config.js    # дизайн-токены (цвета, радиусы) — единая точка для смены стиля
    └── src/
        ├── api/              # типизированный клиент (+ авто-refresh токена)
        ├── context/          # AuthContext
        ├── components/       # ui.tsx (Button, Card, Table, Modal, ProgressBar, Toggle…), Header, Layout
        └── pages/            # Landing, Overview, Payments, Recurring, Budget, Users, Logs, Settings, Docs
```

Слои бэкенда: `handler → service → store → PostgreSQL`. Хендлер не знает про SQL, сервис не знает про HTTP и Telegram.

## Модель данных

- **users** — `login`, `password_hash`, `role` (`admin|user`), `is_system`, `email`, `email_notifications`, `telegram_username`, `telegram_id` и `telegram_verified_at` (заполняются, когда человек подтвердил привязку в боте); **telegram_contacts** — кто писал боту (@имя → чат для запроса на подтверждение). Администратор создаётся/обновляется из `.env` при старте; через API/панель он не изменяется и не удаляется.
- **sessions** — по строке на вход; в JWT лежит `sid`. Logout помечает сессию отозванной, после этого и access-, и refresh-токен перестают работать.
- **recurring_payments** — шаблон: название, сумма, валюта (RUB/USD/EUR), периодичность (`monthly|quarterly|yearly`), `day_of_month`, `first_due_date`, владелец `user_id` (`NULL` — общий платёж, иначе личная подписка), `service_id` (из какой услуги каталога), `trial_until` (конец пробного периода). Удаление — мягкое (`deleted_at`).
- **services** — каталог услуг администратора: название, описание, цена, валюта, периодичность, `trial_days` (0 — оплата сразу при подключении, N — пробный период), `active` (скрыта/видна). Подключение (`POST /services/{id}/subscribe`) копирует условия в новый `recurring_payments` с `user_id` = текущий пользователь; уникальный индекс не даёт подключить одну услугу дважды.
- **payment_occurrences** — **каждый период — отдельная запись**: свой `due_date`, свой `paid_at`, копия названия/суммы/валюты на момент создания, `reminder_sent_at`. Уникальность `(recurring_payment_id, due_date)`. Новый период не затирает прошлые, просрочка не блокирует следующие.
- **audit_logs** — вход, выход, создание/удаление платежей и пользователей, отметки оплаты.

## Ключевые правила (из ТЗ)

| Правило | Где реализовано |
|---|---|
| Статус `paid / unpaid / overdue`, просрочка со следующего дня после срока, оплата в день срока — вовремя | `service/payments.go: decorate` |
| Исправление даты пересчитывает просрочку, срок не меняется; отмена оплаты очищает дату | `PaymentService.UpdateOccurrence` (PATCH) |
| Нет такого числа в месяце → последний день месяца (без «дрейфа» 31→28→28) | `service/schedule.go: DueDateForIndex` (+ тест) |
| Следующие периоды создаются заранее (горизонт — 1 месяц), идемпотентно | `EnsureOccurrences`, тикер в `cmd/server` |
| Суммы по валютам отдельно, без конвертации | `GET /payments/summary`, SQL `GROUP BY currency` |
| Права проверяются в API, а не только в UI | `middleware.RequireRole`, `requireAdmin` в сервисах |
| Видимость: общие платежи — всем, подписка — владельцу и admin | `service.ScopeFor` → `store.Scope` (SQL-фильтр по `rp.user_id`), `canSee` для одного периода |
| Единый часовой пояс | `TZ` в `.env` → `PaymentService.Today()` |
| Удалённый платёж: напоминаний нет, история остаётся | `store.DeleteRecurring`, `DueReminders` фильтрует `deleted_at` |

## Напоминания (Telegram)

Два потока: **общие платежи** — в общий чат (процесс `bot`, ниже), **подписки** — лично владельцу (API-сервер `notify.Hub` отправляет через Bot API в чат пользователя с подтверждённым Telegram, канал `telegram:<user_id>` в `notification_deliveries`). Нажатие «Оплачено» в обоих случаях обрабатывает процесс `bot`: пользователь может отметить только общий платёж или свою подписку. Пока общий чат не задан, общие платежи тоже приходят каждому лично. После создания платежа или подписки рассылка запускается сразу, не дожидаясь минутного тика.

Бот раз в `CHECK_INTERVAL` вызывает `PaymentService.ProcessReminders` (только общие платежи, канал `chat`); API-сервер раз в минуту — `ProcessChannelReminders` для личного Telegram, почты, колокольчика (`app:<id>`) и webhook. Правило одно (`ProcessChannelReminders`):

1. **Ступени** `REMINDER_STAGES=7,3,1` и `od` (просрочено): ступень периода — самая узкая из подходящих (`осталось ≤ 1 дня` → `d1`, `≤ 3` → `d3`, `≤ 7` → `d7`, срок прошёл → `od`). На каждую ступень — одно сообщение в канал. Платёж, добавленный поздно, получает только текущую ступень, пропущенные не досылаются.
2. **Без дублей:** ключ доставки `канал#ступень` вставляется в `notification_deliveries` (первичный ключ `occurrence_id + channel`, `INSERT … ON CONFLICT DO NOTHING` только для неоплаченного периода). Повторная проверка или второй экземпляр ничего не отправит. Ошибка отправки — ключ удаляется, попытка повторится.
3. Оплаченные, удалённые (`deleted_at`) и периоды с чеком на проверке в выборку не попадают.
4. Сообщение: название, сумма, валюта, дата, «Осталось N дней» / «Просрочено», ссылка на платёж (`PUBLIC_URL/payments?open=<id>`) + кнопки **«✅ Оплачено»** и **«🔗 Открыть платёж»** (вторая — если сайт доступен из интернета).
5. После оплаты `notify.Hub` (по событию `payment.paid`) шлёт «✅ Оплата проведена» со ссылкой на чек — тем же получателям, что и напоминания, и в колокольчик.

## Автопродление и разовые платежи (миграция 008)

`recurring_payments.auto_renew` — при `false` `EnsureOccurrences` не создаёт новых периодов; при выключении удаляются неоплаченные периоды после ближайшего (он остаётся к оплате). `period = once` — разовый платёж: один период, продления нет. `PATCH /recurring-payments/{id}` (admin) меняет название, сумму и валюту у неоплаченных периодов со сроком не раньше сегодня; смена периодичности или даты перестраивает будущие неоплаченные периоды. Прошлые и оплаченные периоды не меняются.

## Колокольчик (миграция 008)

Таблица `notifications` (у каждого пользователя свои строки, `read_at`). Пишет `notify.Hub`: напоминания (канал `app:<id>`), события платежа (`payment.created`/`paid`/`unpaid`/`date_fixed`; общий платёж — всем пользователям, личный — владельцу), чек на проверке (администраторам) и решение по чеку (отправителю). Фронтенд опрашивает `GET /notifications` раз в 30 секунд и показывает новые всплывающими сообщениями. Прочитанные старше 60 дней удаляются планировщиком.

## Проверка оплат по чекам (миграция 007)

```
сайт (multipart) ─┐                        ┌─ QR ФНС (gozxing)
                  ├─► ReceiptService.Submit ┼─ pdftotext / pdftoppm
бот (фото/PDF) ───┘        │                ├─ tesseract (OCR, rus+eng)
                           │                └─ ИИ-модель (необязательно)
                           ▼
                 Evaluate: документ · отказ/возврат · сумма · валюта · дата · дубли · замечания ИИ
                           │
          все ok и режим auto ──► approved, ConfirmPaid(дата из чека), журнал receipt_auto_approve
          иначе ──► pending ──► Telegram администраторам (файл + кнопки) и раздел «Проверка»
                                    │
                         approve / reject (причина) ──► пользователю в Telegram/почту
```

- `payment_receipts` — файл (BYTEA), SHA-256, распознанные поля, `checks` (JSONB), статус и решение, снимок платежа
  (название, сумма, валюта, срок, владелец). FK на период — `ON DELETE SET NULL`: архив чеков не теряется.
- Пакет `internal/receipt` только извлекает данные; решение принимает `service` — правила тестируются отдельно (`receipts_test.go`).
- Система не отклоняет чеки сама: любая неуверенность — к администратору. Решение атомарно (`WHERE status = 'pending'`) —
  двойное нажатие в боте и на сайте не создаст два решения.
- Пока по периоду есть чек на проверке, напоминания по нему не отправляются.
- Файл отдаётся только владельцу и администратору, с `X-Content-Type-Options: nosniff` и `Content-Security-Policy: sandbox`.

## Безопасность

- Без токена любые данные и страницы панели недоступны (`401`); пользователь получает `403` на все действия администратора даже прямыми запросами к API.
- Пароли — bcrypt; JWT HS256 (access 15 мин, refresh 7 дней) + проверка живой сессии в БД.
- Секреты только в `.env` (в репозитории — `.env.example`).

## Что можно добавить дальше

Календарь оплат, email/webhook-оповещения, бюджет на месяц/год, чек/ссылка на оплату — каждая фича ложится на существующие слои (новая таблица + сервис + хендлер); другие периодичности добавляются в `DueDateForIndex`.

## Дополнительные каналы и данные (миграция 002)

- **budgets** — `currency`, `period` (`month|year`), `amount`, `user_id` (NULL — общий бюджет). Уникально по (пользователь, валюта, период).
- **app_settings** — key/value: `webhook_url`, `telegram_chat_id` (привязывается командой `/start`), `telegram_bot_username` (пишет бот). Значения из `.env` важнее.
- **notification_deliveries** — (`occurrence_id`, `channel`) — кому уже ушло напоминание: `email:<user_id>`, `webhook`. Захват — `INSERT … SELECT … WHERE paid_at IS NULL ON CONFLICT DO NOTHING`, поэтому дублей нет даже при параллельных проверках.
- **payment_occurrences.receipt_url** — ссылка на чек.
- **audit_logs** — `entity_type`, `details JSONB`, `user_agent`.

События платежей идут через интерфейс `service.EventSink`; его реализует `notify.Hub` (асинхронная отправка на webhook). Напоминания по email/webhook рассылает API-сервер раз в минуту, Telegram — отдельный процесс `bot`.
